# Работа с проектом

## Структура контекста

Для каждого проекта существуют два отдельных репозитория:

* репозиторий **Wiki** — долговременные технические знания проекта;
* репозиторий **Context** — рабочий контекст AI-агента.

Репозиторий Context подключён к основному репозиторию проекта как git submodule.

```text
project/
├── ...
└── context/          → project-context
```

Wiki является отдельным репозиторием и не является частью рабочего дерева основного репозитория.

## Работа с Wiki

Wiki является источником долговременных технических знаний проекта.

Агент:

* может читать Wiki;
* должен учитывать её при восстановлении контекста;

Wiki должна оставаться лаконичной и содержать только ключевые долговременные знания проекта.

## Работа с Context

Context является рабочим контекстом AI-агента.

Базовый Context находится в ветке `dev` репозитория Context.

Перед началом работы агент должен создать feature branch от актуального `dev` репозитория Context.

```text
context/dev
    ↓
context/<feature-branch>
```

После этого агент развивает Context в своей feature branch, используя:

* базовый Context из `dev`;
* Wiki;
* текущую реализацию проекта;
* Issue и комментарии;
* знания и результаты, полученные в процессе выполнения задачи.

Context должен отражать знания, необходимые для продолжения разработки.

AI может самостоятельно создавать, изменять и удалять файлы Context в рамках своей feature branch.

После завершения работы изменения Context должны быть включены в PR Context:

```text
context/<feature-branch> → context/dev
```

## Перед началом работы

Перед началом реализации необходимо полностью восстановить контекст проекта.

Реобходимо прочитать все файлы wiki. 
А так же найти где находится контекст.

После этого необходимо изучить:

* Issue и комментарии, если они существуют;

Контекст должен быть восстановлен **до внесения изменений в код**.

## Анализ задачи

Перед изменением кода необходимо определить:

* что именно требуется изменить;
* какие компоненты затрагиваются;
* какие существующие контракты должны быть сохранены;
* какие контракты или архитектурные решения изменяются;
* какие тесты должны быть добавлены или изменены;
* какие изменения должны быть отражены в Context;

## Реализация

Изменения должны выполняться последовательно и минимально необходимым объёмом.

Новые решения должны соответствовать существующей архитектуре проекта, если задача явно не требует её изменения.

Если в процессе реализации появляется новое техническое знание, необходимое для дальнейшей работы, оно должно быть отражено в Context.

## Во время работы

Если получена новая информация, имеющая значение для текущего тикета или последующей разработки, она должна быть:

1. отражена в Context, если относится к рабочему контексту;
2. отражена в Issue, если относится к текущей задаче;
3. отражена в Wiki, если имеет долговременное архитектурное или техническое значение.

К такой информации относятся:

* архитектурные решения;
* изменения архитектуры;
* изменения контрактов;
* зависимости между компонентами;
* важные ограничения;
* результаты исследований;
* принятые технические решения;
* обнаруженные особенности существующей реализации;
* решения, которые необходимо учитывать в следующих итерациях.

## Issue

Issue описывает задачу и её текущий рабочий процесс.

Если Issue существует, агент должен поддерживать её актуальность в процессе работы.

Если Issue отсутствует, агент **не должен создавать её самостоятельно**.

Перед завершением работы в существующем Issue необходимо зафиксировать существенные результаты работы.

## Проверка

Перед завершением работы необходимо:

1. выполнить тесты, относящиеся к изменённому коду;
2. выполнить необходимые интеграционные тесты;
3. выполнить общие проверки проекта, если они предусмотрены;
4. исправить обнаруженные проблемы;
5. повторно выполнить проверки после исправлений.

PR нельзя создавать при наличии известных неисправностей, относящихся к выполненной задаче.

## Обновление Context

После завершения реализации агент должен проверить Context и привести его в актуальное состояние.

В Context должны быть сохранены знания, необходимые для продолжения разработки.

Устаревшая или опровергнутая информация должна быть удалена или исправлена.

Context не должен превращаться в историю всех изменений.

После этого агент должен:

1. закоммитить изменения в feature branch Context;
2. push feature branch Context;
3. создать PR из feature branch Context в `dev`.

## Обновление submodule

Основной репозиторий проекта должен ссылаться на конкретный commit Context.

Поэтому после изменения Context необходимо обновить submodule в feature branch основного репозитория.

Изменение Context должно привести к изменению staged-состояния submodule:

```text
context @ old-commit
        ↓
context @ new-commit
```

Изменение этого указателя должно быть включено в PR основного репозитория.

Таким образом, PR основного репозитория фиксирует точную версию Context, использованную для реализации задачи.

## Feature branch

Для реализации задачи используется одна feature branch основного репозитория.

В ней должны находиться все изменения, необходимые для реализации задачи, включая обновление commit submodule Context.

Отдельные feature branches для отдельных частей одной задачи без необходимости создавать не следует.

## Связь Issue и PR

**Issue** описывает задачу и её текущий рабочий процесс.

**PR** содержит конкретный набор изменений, реализующий задачу.

PR должен ссылаться на соответствующий Issue, если Issue существует.

## Завершение задачи

Задача считается полностью завершённой только после выполнения всех условий:

* код реализован;
* Context актуализирован;
* изменения Context отправлены в remote;
* создан PR Context → `dev`;
* submodule Context обновлён в feature branch основного репозитория;
* тесты пройдены;
* необходимые проверки пройдены;
* Issue актуальный, если Issue существует;
* в Issue указано, как проверить работоспособность;
* предложены необходимые изменения Wiki, если они обнаружены;
* feature branch основного репозитория отправлена в remote;
* создан PR feature branch → `dev`.

Создание PR является обязательным финальным действием и **не требует дополнительного подтверждения оператора**.
